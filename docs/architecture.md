# Архитектура веб-версии SAPR-BAR

## 1. Решение по платформе

Первый релиз — статическое client-side приложение. Сервер **не нужен**: расчёт умеренного размера выполняется в браузере, а проекты открываются и сохраняются через File API/обычную загрузку файла. Это обеспечивает офлайн-работу, приватность моделей и простой деплой на любой статический хостинг.

В v1 отсутствуют регистрация, аккаунты, база данных, облачное хранение, аналитика и платные сервисы. Сервер добавляется только при подтверждённой необходимости: совместная работа, централизованное хранение, тяжёлые расчёты сверх браузерного лимита или организационные требования. Расчётный API при этом должен оборачивать то же ядро, а не дублировать формулы.

## 2. Технологический стек

| Слой | Выбор | Причина |
|---|---|---|
| Язык | TypeScript, strict mode | один типизированный язык для UI, адаптеров и переносимого ядра |
| Сборка | Vite | простой dev/build без серверного фреймворка |
| UI | React | предсказуемые формы/состояние и зрелая экосистема |
| Графика | SVG | интерактивная 2D-схема, точные подписи, удобный DOM и экспорт |
| Состояние | React state + небольшой доменный store | не вводить тяжёлую инфраструктуру до необходимости |
| Расчёт | чистый TypeScript в отдельном package + Web Worker | тестируемость и отсутствие зависимости от UI |
| Проверка схем | JSON Schema + лёгкий валидатор на файловой границе | версионирование и безопасное открытие файлов |
| Тесты | Vitest; Playwright для сквозного сценария | единый быстрый контур и проверка браузера |
| Численный oracle | Python/NumPy вне production | независимая реализация для сверки |
| Формат проекта | JSON UTF-8 | прозрачен, версионируем, пригоден для миграций |

Конкретные версии зависимостей выбираются при инициализации проекта и фиксируются lock-файлом. До появления реальной проблемы не добавляются canvas/WebGL, WASM, backend-фреймворк или монорепо-оркестратор.

## 3. Границы модулей

```text
apps/web
  UI, команды редактора, визуализация, локализация
       │ domain DTO / use cases
       ▼
packages/model
  сущности проекта, единицы, валидация, хэш входа
       │ AnalysisInput
       ▼
packages/solver
  чистое линейно-статическое ядро, без DOM/React/файлов
       │ AnalysisResult
       ▼
apps/web/results
  таблицы, деформированная схема, эпюры

packages/file-project
  JSON schema, чтение/запись, миграции

packages/file-legacy
  будущие CN/LD/MD-адаптеры; не импортируются solver-ом

workers/analysis-worker
  транспорт сообщений UI ↔ solver
```

Правило зависимостей: UI зависит от use-case/model API; solver зависит только от собственных численных типов и model-contract; файловые адаптеры преобразуют внешний формат в доменную модель и обратно. Solver никогда не читает JSON, CN/LD/MD и не форматирует единицы для экрана.

## 4. Контракты

### 4.1 `AnalysisInput`

Неизменяемый нормализованный снимок в SI: узлы, элементы с уже разрешёнными `E/A/Iz`, освобождения, закрепления и один случай поддерживаемых нагрузок. Он не содержит названий UI, строковых чисел, настроек масштаба или legacy-полей.

### 4.2 `AnalysisResult`

Дискриминированный результат:

```text
{ ok: true, solverVersion, inputHash, diagnostics, displacements,
  reactions, elementEndForces, sampledDiagrams, equilibrium }

или

{ ok: false, solverVersion, diagnostics[] }
```

При `ok:false` массивов «результатов» нет. Диагностика содержит стабильный код, severity, русское сообщение и ссылки на объекты модели.

### 4.3 Численная библиотека

Внутри solver отдельно размещаются:

- матрица/вектор и проверяемый линейный решатель;
- матрица элемента без освобождений;
- статическая конденсация освобождений;
- эквивалентные узловые нагрузки;
- преобразование координат и сборка;
- граничные условия;
- восстановление реакций/усилий/эпюр.

Для v1 допустима плотная симметричная матрица ради прозрачности, но цель 1500 степеней свободы требует замера. Если бюджет 2 секунд не выполняется, реализация матрицы заменяется на разреженную за тем же интерфейсом. UI и файловые адаптеры меняться не должны.

## 5. Поток данных

1. Команда UI изменяет редактируемую доменную модель через проверяемую операцию.
2. Любое изменение входа инвалидирует кэш результатов.
3. Перед расчётом model-validator создаёт диагностику и нормализованный `AnalysisInput` в SI.
4. Снимок структурно клонируется в Web Worker.
5. Solver возвращает успех или структурированную ошибку.
6. UI принимает результат только если `inputHash` совпадает с текущей моделью.
7. Представление переводит SI в выбранные единицы только на последнем шаге.

Гонки исключаются идентификатором задания: поздний результат старого расчёта отбрасывается.

## 6. Сохранение и безопасность файлов

- открытие проекта сначала валидирует JSON и `schemaVersion`, затем мигрирует копию; текущий проект не портится при ошибке;
- лимиты размера файла, числа сущностей и глубины JSON проверяются до построения UI;
- внешние строки показываются как текст, не как HTML;
- файл не может задавать URL, исполняемый код или имя модуля;
- кэш результатов принимается только при совпадении `inputHash` и версии solver-а, иначе игнорируется;
- экспорт атомарно формирует новый Blob и не перезаписывает исходник без действия пользователя.

Legacy-адаптер обязан быть отдельным недоверенным входным слоем: CP866-декодирование, строгий парсер, диагностируемые неоднозначности и явный профиль единиц. Никакие EXE/BAT не запускаются.

## 7. Тестовая архитектура

Пирамида проверок:

- unit: единицы, геометрия, матрицы элемента, поворот, нагрузки, конденсация, линейный решатель;
- property/invariant: симметрия, равновесие, суперпозиция, преобразование/перенумерация;
- golden numeric: утверждённые аналитические и независимо рассчитанные примеры;
- integration: Project → AnalysisInput → solver → result-view model;
- file tests: round-trip JSON, миграции, повреждённые и будущие версии;
- E2E: полный сценарий пользователя и отображение ошибки механизма.

Численные сравнения используют пару абсолютного и относительного допусков; округлённые строки UI не сравниваются вместо чисел.

## 8. Возможное развитие

Новые виды анализа реализуются отдельными use case/solver-модулями и получают собственные контракты результатов. Динамика не должна усложнять линейный статический solver заранее. Если позже нужен сервер, статический frontend остаётся рабочим, а транспорт выбирается на уровне use case; доменная схема, solver и тестовые векторы сохраняются.


## Модуль сечений
src/sections/geometry.ts, calculate.ts, types.ts, catalog.ts — геометрия в SI без React/DOM. projectSection.ts — адаптер выбранной плоскости и проверка согласованности при импорте. Редактор, чертёж и отчёт используют одну геометрию и общее форматирование. Проект хранит необязательную геометрию; .saprsection.json также хранит единицы редактора.
